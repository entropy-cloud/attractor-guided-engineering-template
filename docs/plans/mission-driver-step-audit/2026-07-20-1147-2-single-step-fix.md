## Current Baseline

Live baseline verified against the repo on 2026-07-20:

- `--step <STEP>` 现有实现（`tools/mission-driver/src/main.js:583-597`）做的是**就地改写 flow 对象的 `transitions`**：遍历 `step.transitions`，把所有非 retry 的 `t.goto` 改写成 `t.done = "completed"` 并 `delete t.goto`。
- 该改写**只覆盖 `transitions`**，漏了三类异常出口：
  - `onError`（步骤抛错的兜底）
  - `onUnknown`（marker 无法识别且纠正失败的兜底）
  - `onMaxRetries`（retry 达到上限的兜底）
- 以 `DRAFT_PLANS`（`flows/mission-driver.json:59-71`）为例：`onError: { retry: "DRAFT_PLANS" }`、`onUnknown: { goto: "DEEP_AUDIT" }`、`onMaxRetries: { goto: "DEEP_AUDIT" }` 全都没被改写。AI 输出一个无法识别的 marker → `onUnknown` 把控制流送进 `DEEP_AUDIT` → 回到 `DRAFT_PLANS` → 单步模式退化成完整循环。这正是"指定单步却还是固定步骤执行"的直接根因（设计文档 §2.1）。
- 改写是对**共享 flow 对象的就地 mutation**，靠"每次 run 都是新进程"侥幸避免污染，语义不干净。
- `engine.run(entryOverride)`（`engine.js:1278`）的循环上界当前只有 `maxTotalSteps`（`while (totalSteps < maxTotalSteps)`），无单步上界。
- engine 通过 `this.delegates.config`（即 `cfg`）接收运行参数；`cfg.singleStep` 字段当前不存在，可自由新增。
- `main.js:617` 的 `exitMap`：`{ completed: 0, failed: 1, max_cycles: 2, max_total_steps: 2, max_retries: 2 }`，无 `single_step_done` 映射。
- `--step` option 已在 `run` 子命令注册（`main.js:710`：`.option("--step <step>", ...)`）；`config.entryStep` 由该 option 填充并传入 engine。
- 验证命令：`npm --prefix tools/mission-driver test`。现有 `test/skip-steps.test.js` 覆盖 `--fast` / `--skip-steps` 语义，须确认不破坏。

**Gap:** 单步执行靠 transition 改写，任何异常出口（onError/onUnknown/onMaxRetries）都会让控制流逃出"单步"边界。本 plan 废除改写，改用引擎级 `maxSteps = 1` 硬上界，无论哪条出口都物理上只跑一步。

## Goals

- `--step X` 无论 X 的哪条出口（`transitions` / `onError` / `onUnknown` / `onMaxRetries` / retry）触发，都**物理上**只跑一步就停。
- flow 对象保持不可变——删除 transition 就地 mutation 整段。
- 新退出 status `single_step_done` 在 `main.js` exitMap 映射到 exit code 0（视同成功完成）。

## Non-Goals

- 不新增 `--from-step`（WI3 范围，紧接本 plan）。
- 不改 `--fast` / `--skip-steps` 语义（`engine.js` `effectiveSkip` Set 不动）。
- 不改 `--step` 指向不存在 / 子流程内部 step 的报错文案（现有 `main.js:585-589` 报错逻辑保留，仅删除其后的 mutation 段）。
- 不改子流程内部步骤作为单步入口时的内部 `when` 行为（设计文档 §2.1 备注：孤立单步时子流程内部 when 可能不满足导致 skip，属子流程自己的事，不算 bug）。

### Phase 2 - 引擎 maxSteps 上界与新 status

Status: completed
Targets: `tools/mission-driver/src/engine.js`（`run()` :1278-1324）
Skill: none

- Item Types: `Add | Decision`
- Prereqs: Phase 1 完成

- [x] Decision: 单步退出 status 命名为 `single_step_done`，理由：
      - 选择：新增独立 status，不复用 `completed`。
      - 备选：复用 `completed`。否决理由：`completed` 语义是"mission 正常跑完"，单步调试不是；monitor / 日志 / 复盘需要能区分"这是一次单步调试"与"mission 完成"。设计文档 §4.3.1 明确要求区分。
      - 残留风险：新 status 若未被所有消费方识别可能显示为 unknown。对策：exitMap 已在 Phase 1 映射到 0；monitor 侧展示属 WI5 范围，本期不要求 monitor 识别 `single_step_done`（旧 monitor 显示 unknown 不影响引擎正确性，可在 WI5 收尾）。
      - 关联副作用（已核查，非阻塞但需知晓）：`_result("single_step_done")` → `_finalizeWorkflow(finalStatus)`（engine.js:466）→ 因 `finalStatus !== "completed"`，`_wfClose(null, "failed")` 会把那条单步的 step 记录标成 `status: "failed"`（engine.js:397），即使该步实际成功。这是现有 `_finalizeWorkflow` 语义对非-completed 终态的固有行为，monitor/复盘会看到"成功单步却标 failed"。本期不修（属 run-state step 记录精度问题），由 WI5 可观测性收尾时评估是否给 `_finalizeWorkflow` 加 `single_step_done → completed` 的 step 级映射。
      - Skill: none
- [x] Add: 在 `engine.run()`（`engine.js:1278-1288` 区域，紧挨 `maxTotalSteps` 声明）新增 `const maxSteps = cfg.singleStep ? 1 : Infinity;`。
      - Skill: none
- [x] Add: 把主循环条件从 `while (totalSteps < maxTotalSteps)` 改为 `while (totalSteps < maxTotalSteps && totalSteps < maxSteps)`。
      - Skill: none
- [x] Add: 在循环自然退出（条件不满足而退出，非 `return`）后、`return await this._result(...)` 处，区分退出原因：
      - 若 `cfg.singleStep && totalSteps >= maxSteps` → `return await this._result("single_step_done", totalSteps)`。
      - 否则保持原 `max_total_steps` 行为。
      - 实现注意：当前 `run()` 末尾的"循环正常退出"分支需定位确认（`engine.js:1288` `let totalSteps = 0` 与 `:1324` `while`）；若循环因条件退出而非内部 `return`，落到函数尾部的默认 return，需在那里加分支判断。实现时以实际代码结构为准。
      - Skill: none

Exit Criteria:
