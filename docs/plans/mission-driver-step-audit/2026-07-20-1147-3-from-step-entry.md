## Current Baseline

Live baseline verified against the repo on 2026-07-20（含 WI2 落地后的预期形态）:

- `engine.run(entryOverride)`（`tools/mission-driver/src/engine.js:1278`）**已支持任意入口覆盖**：`let currentStep = entryOverride || this.flow.entry;`。WI3 无需引擎改动。
- CLI 层当前只有两种入口模式：
  - 不传 `--step`：从 `flow.entry`（`CHECK`）开始，正常循环。
  - 传 `--step X`：单步（WI2 落地后为 `singleStep: true` + `maxSteps = 1`）。
- **没有**"从 X 开始、之后照常循环"的模式。`--step`（单步停）与该诉求对偶：要的是入口挪到 X、但 transitions 不动、循环继续。
- `run` 子命令 option 注册在 `main.js:706+`；`--step` 在 `:710`。option 模式可复用。
- `getTopSteps()`（`main.js:68-72`）读 `flows/mission-driver.json` 的 `steps` keys，天然只返回主流程 step（不含子流程内部步骤如 `MULTI_AUDIT`）。
- 现有 `config.entryStep` 由 `--step` 填充。WI2 落地后 `config.singleStep` 在 `--step` 时为 true。
- `main.js:583-597` 在 WI2 落地后：step 存在性校验保留、transition mutation 已删除、改为设 `config.singleStep = true`。
- 验证命令：`npm --prefix tools/mission-driver test`。
- 顶部步骤间不传参（设计结论 #8），各自从磁盘读数据，因此任何顶部步骤都能作为入口（设计文档 §4.3.3 白名单：CHECK / REVIEW_PLANS / EXEC_PLANS / DRAFT_PLANS / DEEP_AUDIT 均安全）。

**前置依赖：** WI2 必须先落地。原因：WI2 把 `--step` 的语义从"transition 改写"改为"`config.singleStep = true` + 引擎 `maxSteps = 1`"，并保留了 `config.singleStep` 这一显式 flag。WI3 的 `--from-step` 需要显式设 `config.singleStep = false` 来与 `--step` 区分——若 WI2 未落地，`--step` 仍靠 transition mutation，`--from-step` 将无法干净复用同一套入口覆盖逻辑，且 transition mutation 会污染共享 flow 对象影响 `--from-step` 的"循环继续"语义。

**Gap:** 缺少"从指定 step 开始、之后照常循环"的 CLI 开关。本 plan 新增 `--from-step`，纯 CLI 层改动，引擎零改动。

## Goals

- 新增 `--from-step <STEP>` option：以 STEP 为入口、transitions 不动、之后照常循环。
- 与 `--step` 互斥（同时传报错）；指向不存在 / 子流程内部 step 时报错并列出可用 step。
- README / help 文本补 `--from-step` 用法。

## Non-Goals

- 不改 `engine.run(entryOverride)`（已支持，零引擎改动）。
- 不改子流程内部步骤作为入口的支持（仍只接受主流程 step；`getTopSteps()` 天然满足）。
- 不强制拦截"以 CHECK 作为 --from-step"（等价默认入口，无害，设计文档 §4.3.3 仅建议提示不强制）。
- 不改 monitor 展示入口覆盖信息（WI5 范围）。
- 不改 audit 计数语义（`--from-step DEEP_AUDIT` 时 `auditRound` 从 0 开始计，属 WI1 字段的自然行为，不在本 plan 改）。
